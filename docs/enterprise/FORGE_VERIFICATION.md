# Verify an original from a Jira issue

Configure the tenant API and database as described in PILOT.md. Each enterprise deployment serves one tenant and one registered Forge installation. Set FRAUDSHIELD_FORGE_REMOTE_URL to the HTTPS origin of this API when deploying Forge. Set FRAUDSHIELD_FORGE_APP_ID in both deployments. On the API set FRAUDSHIELD_FORGE_INSTALLATION_ID and FRAUDSHIELD_FORGE_ENVIRONMENT_ID to the exact ARIs from the intended installation and environment. Set FRAUDSHIELD_FORGE_ACCOUNT_BINDINGS to a server-side JSON object mapping verified Atlassian account IDs to the corresponding provisioned Auth0 subjects. Confirm both identities administratively before adding any mapping. Review mappings after a reinstall and remove them when access ends.

From an issue panel, enter a case UUID and choose Find evidence. Select an item and use Verify and link. Alternatively paste a specific receipt for an older item. The API recalculates SHA-256 over the stored original under the current user's tenant membership. A successful check creates an evidence.verified custody event. Jira then saves the receipt with the current user's issue-edit permission. That write can fail independently after a successful check. Only the reference is shared with issue readers. Verify linked evidence reloads the current issue reference and requests a fresh check. Confluence shows an editor-supplied reference.

For a pilot, have a second investigator install the app on a clean developer site, locate the same item and verify its receipt. Record time to completion against the existing workflow. Repeat with an unmapped account and a viewer, and confirm that neither can check the original. Exercise integrity mismatch only on a disposable synthetic test database. Record the app version, installation, result and elapsed time without capturing access tokens or real evidence. A digest match establishes byte equality with the retained reference; authenticity of the original and a fraud verdict require separate evidence.
